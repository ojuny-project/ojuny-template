# ojuny-template

ojuny-template is a forkable NixOS flake for a single machine. It is built on
the ojuny-desktop modules and organizes the configuration as settings pages, so
the nix-settings-gui menu can edit each option. The flake defines one
`x86_64-linux` system.

## Status

Status: untested. The flake and the setup script exist, and this page describes
them, but no recorded end-to-end run of the install path exists. No version is
tagged, so pin the repository by commit.

## Requirements

- A GitHub fork of this repository. The setup script clones your fork, not the
  upstream copy.
- NixOS with the `nix-command` and `flakes` experimental features enabled. On a
  fresh install they are off, and every flake command fails.
- `git` on `PATH`.
- `python3` is supplied by the setup app wrapper and does not need to be on
  `PATH`.
- `x86_64-linux`. Other systems are unsupported.
- Disk and memory use are not measured. The pre-build step builds fourteen
  targets one at a time to limit peak memory.

## Install and first run

Fork the repository on GitHub, then run the setup app from the upstream flake:

```console
$ nix run github:ojuny-project/ojuny-template#setup
```

The script asks for the git URL of your fork and a clone location, defaulting
to `~/repos/nix-flake`. It then runs `generate-hw`, `generate-user` and
`create-new-system`, which find the `system-hardware`, `users` and host modules
by name and fall back to `modules/00-hardware.nix`, `modules/00-user.nix` and
`modules/00-host.nix`. It adds the
files to git, writes `~/.config/nix-settings-gui/config.json`, and asks whether
to rebuild and reboot, rebuild only, or do neither. A rebuild pre-builds the
compiled targets with `nix build`, then runs `nixos-rebuild boot`.

When the generated files are written, the script prints
`Your Ojuny configuration is ready in <path>`.

The prompts and failure handling are defined in `scripts/setup.sh` and
`docs/03-host-setup.md`. No verified transcript of a full run exists, so a step
may fail on your hardware.

## Configure

Edit the page that owns the setting. Every file with an `@menu` header becomes
one menu in nix-settings-gui, and the `@option` comments on assignments decide
which controls appear. Apply a change with:

```console
$ sudo nixos-rebuild boot --flake ~/repos/nix-flake#ojuny
```

Do not hand-edit the generated hardware module, because `generate-hw`
overwrites it. `docs/module-tree.md` lists every module file in the tree.

The System page also selects package sources. `Package source` switches every
release tool between building from the flake, downloading the newest release
recorded in the repository's `binary-url.json`, and downloading a named release
from that file. Per-tool overrides and release tags sit under Advanced. The
manual has its own selector and defaults to source because it follows the
rolling repository.

## Limits

- One flake describes one host. A second machine needs a second fork or a
  duplicated system directory.
- Partitioning is manual. The template does not use disko, and the generated
  `hardware.nix` describes an existing layout.
- Secure Boot is an optional post-install step for UEFI with systemd-boot. It
  is not enabled by the installer and is not a security guarantee.
- Multiboot is an optional rEFInd helper, off by default. It adds an "Other
  systems" entry and scans internal drives at boot. The installer enables it
  when another internal system is found. It is UEFI only, and it never resizes
  Windows NTFS.
- Recovery is a switch on the Recovery page, on by default. It builds a signed
  recovery UKI and adds an "Ojuny Recovery" firmware entry that boots the
  installed system without systemd-boot or rEFInd.
- Raven is an optional, experimental Windows runtime on the App format
  compatibility page. It is off by default, handles `.exe`, `.msi` and `.bat`
  files, and is not guaranteed to run a given program. `.bat` support is
  best-effort and interactive scripts need a terminal. Failed launches open a
  report dialog; survey mode is debug-only and may break the Raven
  configuration.
- The settings scanner does not reorder keys inside a list, so a setting that
  needs a fixed order must declare it in the module.
- Six patches are pre-included in `modules/patches`: development, docker,
  flatpak, nixshell, remote desktop and virtualization. More can be installed
  with `ojuny-patches`; impermanence is available from the registry.
- The System page selects the kernel. LTS, latest and Zen come from nixpkgs.
  CachyOS latest and LTS use the `nix-cachyos-kernel` input and its binary
  cache. A patch or host can override the choice with a normal
  `boot.kernelPackages` assignment.

## Documentation

- `docs/module-tree.md`: which module files exist, generated by
  `scripts/gen-module-tree.sh`.
- `docs/03-host-setup.md`: what the setup script generates and prompts for.
- `docs/02-settings-menu.md`: how pages, categories and menu headers are
  organized.
- `docs/04-scope.md`: what is ported from dendrite and what is dropped.
- `docs/05-settings-gui-limitations.md`: what the scanner can and cannot read.
- `docs/06-secure-boot.md`: how to enroll keys on supported UEFI hardware.
- `docs/07-lifecycle.md`: machine handover, factory reset, full reset and
  NixOS generation rollback.
- `docs/08-install-time.md`: install-time benchmark protocol and results.
- `docs/09-multiboot.md`: the optional rEFInd helper for other operating
  systems.
- `docs/10-recovery.md`: the optional recovery UKI and firmware boot order.
- `docs/11-agent.md`: the optional maintenance agent, read-only assistant and
  flake-safe agent CLI.
- `docs/12-flake-module-contract.md`: how install and generation tools find
  modules, the `modules/` fallback, the facter location and the flake location.

## Contributing

Report defects in the repository issue tracker at
<https://github.com/ojuny-project/ojuny-template/issues>. A patch must pass
`sh scripts/check-baseline.sh`, keep generated hardware and account data out of
the diff, and regenerate `docs/module-tree.md` when module files change.
